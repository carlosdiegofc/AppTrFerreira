# App/web integration — 0.16.0

Base: Claude 0.12.0, commit e8cc20437fc73ac9cdb82b2ca64ded17ae1ede31.
Android source is app/ at repository root. The nested 0.10.1 folder is historical and is not compiled.

- Trips can start without business fields or GPS permission. Empty returns export empty cargo and kg.
- Current transport vehicle uses the catalog label `tipo · matriculaCamion`; web must prefer unique full label/plate and refuse ambiguous model-only matches.
- Driver histories remain owner-only for drivers. Owner accounts (luis@trferreira.com, transportesferreirauy@gmail.com) read the whole fleet; those reads rely on administrator row security. transportesferreirauy@ opens the fleet panel instead of the driver home. Since 0.16.0 luis@, who also drives, starts like a driver (his own trips are ordinary driver rows under his user id) and reaches the fleet screens through an owner menu. luis@ is in trf_panel_admins (read-only); transportesferreirauy@ is a full administrator. Panel administrators read every driver's receipt and remito photos through the storage policy trf_panel_admin_read_photos (docs/sql/panel_admin_read_photos.sql, applied 2026-10-10); until then only full administrators could open them. Catalog access before first trip is granted through trf_driver_catalog_access to the existing authorized drivers. An administrator must enroll new drivers.
- trf_vehicle_maintenance (vehicle, kind, due_on, done_on, odometer_km, notes) and trf_documents (scope driver|vehicle, driver_id and driver_name or vehicle, kind, expires_on, notes) use the catalog vehicle label. Enrolled drivers read services and truck papers; drivers manage their own papers and the services they created; administrators of either kind manage everything; other accounts see nothing. SQL: docs/sql/app_maintenance_documents.sql.
- panel_data on fuel is authoritative, including moneda. Prices/contact data are never added to mobile catalog.
- pending_documents, synced_at and other local bookkeeping fields must never be sent as database columns.
- Pretrip documents are persisted on the trip and recovered with stable IDs. Failed attachments remain pending and do not stop other records.
- GPS rejects impossible fixes both from distance and map upload. Raw older routes are not rewritten.
- 0.15.0 changes no data exchanged with the web. It targets API 36, no longer declares background location (trip GPS runs in the location foreground service) and is distributed through Google Play; a Play install has a different signature, so the old APK must be uninstalled once after its pending records are sent.
- 0.15.1 publishes under the application ID com.transportesferreira.app (code namespace stays uy.transportesferreira.gps). It installs as a separate app from the old uy.transportesferreira.gps APK; data exchanged with the web is unchanged.
- 0.16.0 adds an interface mode per driver account (simple or normal), chosen after sign-in and stored only on the phone; the fleet-panel account is never asked. A simple-mode trip is the same record as a quick start: the remembered vehicle (or the one from the driver's latest trip), `load_type` loaded and empty details, with GPS origin, arrival, distance and times. Data exchanged with the web is unchanged.
- 0.16.0 also adds a read-only month summary for owners, per truck and per driver. It reads trf_driver_tracking_sessions (by started_at), trf_trip_details, trf_panel_trips (app rows by app_trip_id, manual rows by departure_at) and unarchived trf_driver_fuel_receipts (by recorded_at) and applies the rules of `summarize` in web/js/trips.js: panel values win, rows with deleted_at are left out, UYU and USD are never added together, and litres per 100 km need 300 GPS km in the month. Two additions on the phone only: GPS kilometres are split by `load_type`, and a vehicle label is matched to its catalog truck (plate first; a label without plate must name exactly one model), so per-truck rows can differ from the web summary for trips saved with an older label. The fleet totals are the same.
- The app and website use independent deployments. Build an APK from the desired branch; changing main is not required to test this version.

Validation: workflow runs assembleDebug, JVM unit tests and bundleRelease (signed with the Play upload key from the repository secrets, or a throwaway key when they are missing). Physical GPS, camera, battery restrictions and display remain device acceptance tests.
