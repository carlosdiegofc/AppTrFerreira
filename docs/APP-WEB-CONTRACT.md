# App/web integration — 0.17.0

Base: Claude 0.12.0, commit e8cc20437fc73ac9cdb82b2ca64ded17ae1ede31.
Android source is app/ at repository root. The nested 0.10.1 folder is historical and is not compiled.

- Trips can start without business fields or GPS permission. Empty returns export empty cargo and kg.
- Current transport vehicle uses the catalog label `tipo · matriculaCamion`; web must prefer unique full label/plate and refuse ambiguous model-only matches.
- Driver histories remain owner-only for drivers. Owner accounts (luis@trferreira.com, transportesferreirauy@gmail.com) read the whole fleet; those reads rely on administrator row security. transportesferreirauy@ opens the fleet panel instead of the driver home. Since 0.16.0 luis@, who also drives, starts like a driver (his own trips are ordinary driver rows under his user id) and reaches the fleet screens through an owner menu. luis@ is in trf_panel_admins (not a full administrator; since migration 0001 the panel accounts also save trips); transportesferreirauy@ is a full administrator. Panel administrators read every driver's receipt and remito photos through the storage policy trf_panel_admin_read_photos (docs/sql/panel_admin_read_photos.sql, applied 2026-10-10); until then only full administrators could open them. Catalog access before first trip is granted through trf_driver_catalog_access to the existing authorized drivers. An administrator must enroll new drivers.
- trf_vehicle_maintenance (vehicle, kind, due_on, done_on, odometer_km, notes) and trf_documents (scope driver|vehicle, driver_id and driver_name or vehicle, kind, expires_on, notes) use the catalog vehicle label. Enrolled drivers read services and truck papers; drivers manage their own papers and the services they created; administrators of either kind manage everything; other accounts see nothing. SQL: docs/sql/app_maintenance_documents.sql.
- panel_data on fuel is authoritative, including moneda. Prices/contact data are never added to mobile catalog.
- pending_documents, synced_at and other local bookkeeping fields must never be sent as database columns.
- Pretrip documents are persisted on the trip and recovered with stable IDs. Failed attachments remain pending and do not stop other records.
- GPS rejects impossible fixes both from distance and map upload. Raw older routes are not rewritten.
- 0.15.0 changes no data exchanged with the web. It targets API 36, no longer declares background location (trip GPS runs in the location foreground service) and is distributed through Google Play; a Play install has a different signature, so the old APK must be uninstalled once after its pending records are sent.
- 0.15.1 publishes under the application ID com.transportesferreira.app (code namespace stays uy.transportesferreira.gps). It installs as a separate app from the old uy.transportesferreira.gps APK; data exchanged with the web is unchanged.
- 0.16.0 adds an interface mode per driver account (simple or normal), chosen after sign-in and stored only on the phone; the fleet-panel account is never asked. A simple-mode trip is the same record as a quick start: the remembered vehicle (or the one from the driver's latest trip), `load_type` loaded and empty details, with GPS origin, arrival, distance and times. Data exchanged with the web is unchanged.
- 0.16.0 also adds a read-only month summary for owners, per truck and per driver. It reads trf_driver_tracking_sessions (by started_at), trf_trip_details, trf_panel_trips (app rows by app_trip_id, manual rows by departure_at) and unarchived trf_driver_fuel_receipts (by recorded_at) and applies the rules of `summarize` in web/js/trips.js: panel values win, rows with deleted_at are left out, UYU and USD are never added together, and litres per 100 km need 300 GPS km in the month. Two additions on the phone only: GPS kilometres are split by `load_type`, and a vehicle label is matched to its catalog truck (plate first; a label without plate must name exactly one model), so per-truck rows can differ from the web summary for trips saved with an older label. The fleet totals are the same.
- 0.16.3: Flota en vivo reads the live position with the route rule (readings without trip_id from older versions count inside the trip window) and looks up the last finished trip of each catalog truck past the latest 100. An owner can add a driver paper for another driver. The trf_documents row (scope driver) then carries that driver's driver_id and driver_name, picked from the drivers with trips or papers; created_by stays the owner. documents_insert already allows it for fleet managers. Everything else is on the phone only: the live fleet map matches a trip's vehicle label to its catalog truck the same way as the month summary, so a trip saved with an older label marks that truck as on a trip instead of listing it again as idle; the fuel list keeps loading receipts (newest recorded_at first, up to 2000) until the whole current month is in; its "Este mes" totals keep each currency apart instead of leaving USD out and parse numbers with FleetStats.number(); panel_data on fuel and data on trip details are read as an object or as JSON text, like the month summary and the web; and readings at 0,0 or off the globe are not drawn on the fleet and trip maps, like validLatLng on the web.
- 0.17.0: a reading every 2 s (it was every 3 to 5). The live position (the trf_driver_locations upsert, same columns) goes out alone right after each reading, on its own line, besides the full sync. trf_driver_tracking_sessions is upserted every 15 s while moving (distance_meters and the last reading; that sync starts at once), and at once on pause, resume and finish. The live row is written by one sender at a time, each with the newest reading, so a slower sync never puts an older position back. trf_driver_location_history keeps one reading about every 5 s while moving and one every 30 s while stopped (before: every reading, also while parked), plus the last reading at a pause and at the end (same event_id, so never twice), inserted as one JSON array per sync (every 10 s, on_conflict=event_id with ignore-duplicates; one by one if the batch fails). distance_meters still adds every reading on the phone. The owner's Flota en vivo reads trf_driver_locations every 5 s for the trips in progress (a row counts for a trip when its recorded_at falls inside the trip) instead of the last history reading per trip, and who is on a trip every minute.
- The new web panel (panel/, published under /nuevo/ next to the current one) reads the same tables and writes only trf_panel_trips (next point). Like the current panel it opens only for trf_is_panel_admin(): trf_panel_trips (panel edits and the bin) is readable only by that list, so a full administrator outside it would count deleted trips. It leaves out app trips whose trf_panel_trips row has deleted_at, reads routes with the rule of the current panel (the driver's readings with that trip_id or none, inside the trip window), takes the live position of a trip in progress from its driver's trf_driver_locations row when that row's recorded_at falls inside the trip (every app version updates it with each reading; read every 3 seconds, routes every 5 with only their new readings, trips in progress every 15), looks up the last finished trip of each catalog truck past the latest 100, and applies the app's rules: moving from 5 km/h, no signal after 15 minutes without readings, papers due within 30 days, services within 15, days in Uruguay time. Viajes reads like the current panel's trips: app trips by started_at with their trf_trip_details and their trf_panel_trips row (by app_trip_id), plus manual trf_panel_trips rows by departure_at; panel values win; a trip with deleted_at shows only in the trash and in no total; an older vehicle label is matched to its catalog truck. A trip's page also reads its trf_trip_documents and its unarchived trf_driver_fuel_receipts (panel_data wins) by trip_id, and opens their photos with signed links of 10 minutes from the private buckets.
- Since migration 0001 (supabase/migrations/0001_panel_trips_edicion.sql, applied in production on 2026-10-18), the accounts of trf_panel_admins insert and update trf_panel_trips; nobody deletes (there is no delete policy). Both panels save the same way (web/js/data.js, panel/src/data/api.ts). The first save of an app trip inserts its row: source app, app_trip_id, departure_at (the trip's started_at, which the deleted-trip filters use), driver_id and the office's fields. A manual trip inserts source manual and needs departure_at and vehicle. Later saves update by id where updated_at equals the value read; no row updated, or a unique violation on app_trip_id, means someone else saved first, and the panel reads the trip again without saving. The trash sets deleted_at; restoring sets it back to null. The trigger trf_panel_trips_touch sets updated_at and updated_by on every save and created_at and created_by on insert, and keeps id, source, app_trip_id, created_at and created_by on update. The new panel only takes map points from the trip itself or from its GPS start and end; it calls no geocoding service. The app neither reads nor writes these rows for editing; drivers will edit their own trips from a later app version (decision of 18/10/2026).
- The app and website use independent deployments. Build an APK from the desired branch; changing main is not required to test this version.

Validation: workflow runs assembleDebug, JVM unit tests and bundleRelease (signed with the Play upload key from the repository secrets, or a throwaway key when they are missing). Physical GPS, camera, battery restrictions and display remain device acceptance tests.
